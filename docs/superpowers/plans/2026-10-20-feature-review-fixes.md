### R01 — P1: L1 разрешает прямой маршрут к AI-домену при наличии другого VPN-маршрута

**Место:** `NotchBuddy/Sources/App/HookServer.swift:3488–3500`, генерируемая функция `verify_vpn_route`.

**Сценарий и доказательство:** включён контроль раздельного туннелирования; после последнего здорового снимка L2 маршрут AI-домена меняется на `en0`, маршрут `1.1.1.1` остаётся `utun3`. Хук видит свежий незащищённый маршрут домена, но возвращает `true` по общему маршруту. Подтверждено безопасной подстановкой результатов route. Действие проходит до следующего тика L2, хотя L1 должен остановить его сразу.

**Исправление:** передать политику `splitTunnelCheck` в runtime state и применить её в L1. При включённом контроле явный незащищённый маршрут к известному AI-домену должен приводить к отказу; общий маршрут не должен его отменять. Отдельно определить поведение при невозможности разрешить домен. Сохранить намеренный режим без проверки доменов, когда пользователь выключил эту опцию.

**Связь со старым планом:** текущий fallback прямо описан в плане `2026-10-16-l1-gate-offline-and-split-tunnel.md`. Это пробел в дизайне защиты, а не отклонение реализации от того плана: положительный split tunnel проверялся, обратный случай — нет.

- [x] Добавить регрессию: split-check включён, домен → `en0`, общий маршрут → `utun3`, результат — отказ без ожидания L2.
- [x] Синхронизировать поле политики из watchdog в runtime state; исправить `verify_vpn_route` в генераторе, сохранить разрешение при домене → VPN.
- [x] Прогнать изолированные тесты L1; проверить отказ без отправки сигналов реальным процессам.

### R09 — P2: после закрытия approval ожидающий вопрос не возвращается на экран

### R14 — P2: выключение TunnelGuard оставляет приостановленные процессы без возобновления

### R15 — P2: проверка живости туннеля может пинговать обычный интернет

**Место:** `NotchBuddy/Sources/App/TunnelGuardNetworkWorker.swift:181–185,232–248,278–288`.

**Сценарий и доказательство:** маршрут `1.1.1.1` проходит по `en0`, а `8.8.8.8` или default — по `utun`. Worker выбирает второй маршрут как VPN, но проверяет живость неизменно пингом `1.1.1.1` без привязки интерфейса. **Исправление:** проверять адрес и интерфейс выбранного VPN-маршрута; не делать вывод о его исправности по доступности адреса через другой интерфейс.

### R16 — P2: Telegram на Windows/Linux неверно проходит набор из нескольких вопросов

**Место:** `windows/src-tauri/src/telegram.rs:834–876,919–937`.

**Сценарий и доказательство:** если первый вопрос multi-select, Submit сразу строит ответы для всего набора, включая пустые ответы на ещё не показанные вопросы, и удаляет контекст. Если первый вопрос single-select, а второй multi-select, переход создаёт только кнопки вариантов и не создаёт Submit; ответ на второй вопрос нельзя завершить штатно. Дополнительно сборка итоговых ответов в single-select ветке берёт лишь первый элемент ранее выбранных значений.

Оба основных пути воспроизведены минимальным Rust-harness с неизменённым `handle_update_internal` и подставными API/pipe: первый Submit отправил `Q2=""` и удалил запрос; второй путь открыл Q2 без действия Submit.

**Исправление:** общий генератор клавиатуры и единый переход на следующий вопрос для single/multi/text; отправлять весь набор только после ответа на последний вопрос и сохранять все значения multi-select.

- [x] Исправить переходы и клавиатуры, сохраняя привязку `request_id` и защиту callback.
- [x] Убедиться, что `answer_question` не вызывается до последнего ответа; ни один ответ не пуст и multi не усечён.

### R17 — P2: заявленный отклик гибридного Astral на клик не подключён
